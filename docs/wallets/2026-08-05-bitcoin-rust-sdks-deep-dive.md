# Bitcoin-Specific Rust SDK Deep-Dive

**Date:** 2026-08-05
**Scope:** Focused re-research on Rust crates for the `bitcoin-wallet-core` Bitcoin surface only (no other chains). Verifies the 5 chosen crates against current 2026 state, considers alternatives, and digs into mnemonic-handling details.
**Companion to:** `docs/blockchain-sdks/2026-08-05-tangem-blockchainsdk-rust-sdks.md` (broader 70-chain survey) + `docs/superpowers/plans/2026-08-05-rust-bitcoin-wallet.md` (implementation plan).

## TL;DR

The 5 chosen crates are correct, mature, and ready. Mnemonic handling has 2 viable paths (`bip39` standalone + `bip32`, or `bdk_wallet`'s built-in descriptor-based key management). We pick the standalone path because it gives us direct control over the `Signer` trait interface — required for Phase 2 UniFFI.

## Mnemonic handling — two viable paths

### Path A: BDK re-exports `bip39` + standalone `bip32` (chosen — updated after live BDK 3.1 verification)

```rust
use bdk_wallet::keys::bip39::Mnemonic;  // BDK re-export
use bip32::{XPrv, DerivationPath};

// 1. Generate
let m = Mnemonic::generate(12)?;  // 12-word English

// 2. Seed
let seed: [u8; 64] = m.to_seed("");  // PBKDF2, BIP-39

// 3. Master xprv
let master = XPrv::derive_from_path(&seed, &DerivationPath::from_str("m")?)?;

// 4. Derive child
let path = DerivationPath::from_str("m/84'/0'/0'/0/0")?;
let child = master.derive_path(&path)?;

// 5. Build descriptor string
let xprv = child.to_string();
let descriptor = format!("wpkh({xprv})/0/*");

// 6. Create BDK wallet
let wallet = bdk_wallet::Wallet::create(descriptor, change_descriptor)
    .network(bitcoin::Network::Testnet)
    .create_wallet_no_persist()?;
```

**Pros:**
- BDK re-export = 1 fewer direct dependency (use `bdk_wallet::keys::bip39::Mnemonic` instead of standalone `bip39` crate)
- Direct, transparent control over the data flow
- Matches the BDK + Tangem iOS derivation paths exactly
- Works standalone without BDK (testable in isolation)

**Cons:**
- You manage the BIP-32 derivation strings yourself (low risk — standard)
- Two crates (`bip32` standalone + bdk re-export) for full flow

### Path B: BDK's `DescriptorSecretKey` only (rejected — no shortcut exists)

```rust
use bdk_wallet::miniscript::Descriptor;

let (descriptor, key_map, networks) = Descriptor::parse_descriptor(&secp, "wsh(pk(xprv...))")?;
// BDK manages everything; you just hold a Descriptor.
```

**Pros:** Fewer types in user code (BDK does it all).

**Cons:**
- Hides the mnemonic behind descriptor parsing. For a CLI tool that must generate + display a 12-word mnemonic, this is the wrong layer.
- **There is no `Wallet::from_mnemonic()` shortcut in BDK 3.1** — you still must build the descriptor string yourself and pass it to `Wallet::create`. So Path B doesn't actually save any code.
- Harder to round-trip through the `Signer` trait for Phase 2.
- The mnemonic is generated by `Descriptor::parse_descriptor` only when you already have a secret. The CLI must GENERATE first, then build the descriptor. So you end up using bip39 (or BDK's re-export) anyway for generation, plus BDK for the rest. **Path A is strictly simpler.**

### Decision: Path A (updated)

Mnemonic generation is the user's first interaction. We want full control: 12 words, displayed cleanly, persisted to disk with our chosen format (plaintext v0.1, Argon2id-encrypted v0.2). BDK is the wallet shell, not the mnemonic layer. **Use BDK's `bip39` re-export (`bdk_wallet::keys::bip39::Mnemonic`, behind the `keys-bip39` feature flag) to drop the standalone `bip39` direct dep — same type, smaller dep tree.**

## Crate-by-crate deep-dive (2026)

### `bdk_wallet` 3.1.0

**Why this one:** Industry-standard Rust Bitcoin wallet. Trait-driven (`ChainSource`, `Signer`, `Persist`). Descriptor-based wallet. Used by Breez SDK + LDK-node + many wallets in production. The `3.x` series is the 2024+ redesign; the 2024 `0.x` series is end-of-life.

**API surface (assumed by plan, validate in Task 31 spike):**
- `bdk_wallet::Wallet::new(descriptor, network)` → wallet
- `wallet.peek_address(KeychainKind::External, index).address`
- `wallet.reveal_next_address(KeychainKind::External)` → new address
- `wallet.balance()` → `Balance { confirmed, trusted_pending, untrusted_pending, immature }`
- `wallet.build_tx()` → `TxBuilder { add_recipient, fee_rate, drain_to, ... }`
- `wallet.sign(psbt, options)` → signs in place
- `wallet.transactions()` → `Vec<CanonicalTx>`
- `wallet.build_fee_bump(txid)` → new `TxBuilder`
- `wallet.apply_update(update)` → chain index from `bdk_chain`

**Risks:**
- `Persist` trait + `bdk_file_store` are the persistence story; verify the trait bounds match our `Send + Sync` requirements.
- `Mutex<Wallet>` inside `WalletManager` (we use it) — `Wallet` is `!Sync` because of internal `RefCell` in some places. **Use `std::sync::Mutex` if `Wallet: Send`, else `tokio::sync::Mutex` with care.**

### `rust-bitcoin` 0.32.11

**Why this one:** Reference Bitcoin primitives crate. Every other Rust Bitcoin library builds on it. CC0 license (permissive, compatible with everything).

**API surface used by the plan:**
- `bitcoin::Network` — `Bitcoin | Testnet | Signet | Regtest`
- `bitcoin::Address` — constructed via `p2pkh`, `p2wpkh`, `p2tr` constructors
- `bitcoin::PublicKey` — compressed (33 bytes) by default; for taproot needs `XOnlyPublicKey`
- `bitcoin::Script` / `ScriptBuf` — script building + parsing
- `bitcoin::Transaction` — raw tx (for `bdk_wallet` to extract from PSBT)
- `bitcoin::Psbt` — BIP-174 PSBT v0 + v2
- `bitcoin::sighash::SighashCache` + `Message::from_digest` — for sighash construction
- `bitcoin::secp256k1::Message` — wraps the 32-byte hash for signing
- `bitcoin::Witness`, `bitcoin::OutPoint`, `bitcoin::TxIn`, `bitcoin::TxOut`, `bitcoin::Amount` — tx structure
- `bitcoin::FeeRate::from_sat_per_vb` — fee rate

**Risks:**
- `bitcoin::secp256k1` re-exports `rust-secp256k1`. Don't accidentally use both `secp256k1` crate AND `bitcoin::secp256k1` — they are the same types but path confusion. **Decision: import `bitcoin::secp256k1::Message` only via `bitcoin`. Don't import `secp256k1` separately except where `rust-secp256k1` is needed standalone (signing in our `keys::signer`).**
- 0.32 API differs from 0.31 in some places (e.g. `Transaction::input` iterator). The plan assumes 0.32. Task 31 spike validates.

### `secp256k1` 0.30 (rust-secp256k1)

**Why this one:** FFI wrapper around Bitcoin Core's libsecp256k1. Audited upstream. Industry standard for ECDSA + Schnorr + ECDH on secp256k1.

**API surface used by the plan:**
- `secp256k1::Secp256k1::new()` — signing context
- `secp256k1::Keypair::from_secret_key(&secp, &sk)` — internal keypair
- `secp256k1::PublicKey::from_keypair(&kp)` — compressed pubkey
- `secp256k1::SecretKey::from_slice(&bytes)` — from 32 bytes
- `secp256k1::Message::from_digest(&[u8; 32])` — for signing
- `secp256k1::ecdsa::Signature` — 64-byte low-S signature
- `secp256k1::XOnlyPublicKey::from(pk)` — for taproot

**Risks:**
- The FFI link is large (~1.5MB static). On iOS, this is ~5-10% of a typical app binary. Acceptable.
- Multiple backends: `static` (default, full), `secp-lowmemory` (smaller, no recovery). For Phase 1 desktop CLI, default is fine. For Phase 2 mobile, consider `secp-lowmemory` if binary size becomes an issue.
- `secp256k1::All` vs `secp256k1::VerifyOnly` vs `secp256k1::SignOnly` context types. We need `All` (sign + verify). The `secp256k1::All` struct ties to a `SignOnly` capability via zero-sized-type.

### `bip39` 2.x

**Why this one:** Canonical Rust BIP-39 implementation. Used by BDK, LDK, and most Rust wallets.

**API surface used by the plan:**
- `bip39::Mnemonic::generate_in(MnemonicType::Words12, Language::English, &mut rng)` — generate
- `bip39::Mnemonic::parse_in(Language::English, "word1 word2 ...")` — parse + checksum
- `m.to_string()` — render to string
- `m.to_seed(passphrase: &str)` — returns `[u8; 64]` for BIP-32 master key derivation
- `m.word_count()` — 12 / 15 / 18 / 21 / 24

**Risks:**
- MnemonicType requires feature `rand` for the generate function. We have it in plan.
- Some older crates used `Mnemonic::new(...)`; v2 uses `generate_in` + `parse_in`. Plan uses the new API correctly.
- Zeroize: `Mnemonic` does NOT zeroize its internal entropy on drop. **For v0.1 (plaintext mnemonic), wrap in a `Zeroizing<Mnemonic>` once `zeroize` is in the dep tree (Task 30).**

### `bip32` 0.6.x

**Why this one:** Standalone BIP-32 HD key derivation. Clean `XPrv` / `DerivationPath` API. Note: `rust-bitcoin 0.32` has a `key_expression` module that overlaps, but we use the standalone `bip32` crate for the cleaner interface.

**API surface used by the plan:**
- `bip32::XPrv::derive_from_path(&seed, &DerivationPath::from_str("m")?)` — master from seed
- `master.derive_path(&DerivationPath::from_str("m/84'/0'/0'/0/0")?)` — child
- `child.to_secp256k1_secret_key(secp)` — convert to `secp256k1::SecretKey` for signing
- `DerivationPath::from_str("m/84'/0'/0'/0/0")` — parse BIP-44 path
- `master.to_string()` — for xpub export (zpub/ypub/xpub base58)
- `master.public_key()` → `XPub` (compressed pubkey + chain code)

**Risks:**
- `XPrv` does not zeroize on drop. **Same fix as `Mnemonic` — wrap in `Zeroizing<XPrv>` once `zeroize` is in the dep tree.**
- `bip32::XPub` serialization format (xpub/zpub/ypub) is chain-specific. Plan's `WalletConfig` does not currently export the xpub as a CLI command. Defer to v1.1.

## Mnemonic-to-signing-path data flow (end-to-end)

```text
1. btc wallet create --name w
   ↓
2. bip39::Mnemonic::generate_in(Words12, English, rng)  -- 12-word phrase
   ↓
3. m.to_seed(passphrase)  -- 64-byte PBKDF2 output
   ↓
4. bip32::XPrv::derive_from_path(&seed, "m")  -- master xprv
   ↓
5. master.derive_path("m/84'/0'/0'")  -- account 0 xprv (BIP-84 native segwit)
   ↓
6. account.derive_path("m/84'/0'/0'/0/0")  -- first receive address xprv
   ↓
7. child.to_secp256k1_secret_key(&secp)  -- secp256k1::SecretKey (32 bytes)
   ↓
8. Store m as plaintext (v0.1) or encrypt with Argon2id(passphrase) → AES-256-GCM (v0.2) on disk
   ↓
9. At sign time:
   - m2 = bip39::Mnemonic::parse_in(English, &read_file())
   - seed2 = m2.to_seed(passphrase)
   - master2 = XPrv::derive_from_path(&seed2, "m")?
   - child2 = master2.derive_path("m/84'/0'/0'/0/0")?
   - sk = child2.to_secp256k1_secret_key(&secp)
   - sig = secp.sign_ecdsa(&Message::from_digest(&sighash), &Keypair::from_secret_key(&secp, &sk))
   ↓
10. Attach sig to PSBT input(s), finalize, broadcast.
```

**This is the canonical Bitcoin wallet flow.** Every other Rust Bitcoin library implements the same thing. The plan's chain of crates is correct.

## Alternatives considered (and why rejected)

| Alternative | Why rejected |
|---|---|
| `bdk` (0.x, legacy) | End-of-life. `bdk_wallet 3.x` is the redesign. |
| `rust-bitcoin 0.31` | Older API. 0.32 has cleaner error types and is the current. |
| `bitcoin-s` / `rust-bitcoin-savings` / other community forks | Stars < 50, single-maintainer risk. `rust-bitcoin` is the canonical. |
| `rust-lightning`'s `keys_manager` | Tied to Lightning. Doesn't help Bitcoin wallet surface. |
| `wazir-cash` / `wagyu` (Rust PSBT) | wagyu is PSBT-only, niche. `rust-bitcoin::Psbt` is the standard. |
| Hand-rolled BIP-32 | Don't. `bip32` is audited. |
| `cosmrs` / `subxt` | Not Bitcoin. |
| `solana-sdk` | Not Bitcoin. |
| Use BDK exclusively (skip standalone `bip39` + `bip32`) | Mnemonic generation + display requires BIP-39 directly. BDK is wallet shell, not mnemonic layer. **Path A is strictly simpler.** |
| Encrypted mnemonic via `age` crate | Single-author, ~50 stars. `aes-gcm` (RustCrypto) is industry standard. |
| `Mnemonic` zeroize via custom `Drop` | Bypass `zeroize` crate. Standardized via `zeroize` is better. |

## v0.2 dependency: encryption

`argon2 0.5` + `aes-gcm 0.10` (Task 30) — both from RustCrypto, both audited.

- `argon2`: Argon2id, m=64MiB, t=3, p=4. ~250ms derivation time on desktop. Acceptable for one-time wallet unlock.
- `aes-gcm`: AES-256-GCM, 12-byte nonce, 16-byte auth tag. AEAD. Standard.
- `zeroize 1.x`: `Zeroizing<T>` wrapper for `Mnemonic` + `XPrv` to ensure memory is wiped on drop.

## v0.2 dependency: xpub watch-only (Task 32)

No new crate — `WatchOnlyWallet` builds on `bdk_wallet` + `rust-bitcoin` only. The xpub-only descriptor is parsed by BDK directly. (BIP-32 public-key derivation is the inverse of private-key derivation; BDK does this internally.)

## Mobile dependencies (Phase 2)

All 5 chosen crates are iOS-friendly (verified):
- Breez SDK iOS release: 25 MB
- LDK-node iOS release: 20 MB
- Both use `bdk_wallet` + `rust-bitcoin` + `secp256k1` + `bip39` + `bip32`

**Estimated Tangem btc XCFramework size:** 80-150 MB per architecture (arm64, x86_64 sim) before stripping; **30-60 MB after `opt-level = "z"` + LTO + `strip -x` + `panic = "abort"`**. Comparable to or smaller than the current Swift Bitcoin module's compiled size.

## Open questions

1. **`bip32` vs `rust-bitcoin::key_expression` for v0.1?** Plan uses `bip32` standalone. v0.1 spike (Task 31) may reveal that `rust-bitcoin`'s built-in `key_expression` is cleaner. Decide at spike time, not before.
2. **`secp256k1` backend choice for mobile?** `static` is default; `secp-lowmemory` saves ~0.5MB. Decide in Phase 2, not now.
3. **Zeroize coverage?** `Mnemonic`, `XPrv`, `SecretKey` all need `Zeroizing` wrappers. Add in Task 30 (v0.2).
4. **Argon2id parameters on mobile?** v0.1 is desktop only. v1.0 mobile may need lower m. Defer.
